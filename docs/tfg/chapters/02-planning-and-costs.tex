\chapter{Planificación y costes}
\label{chap:planning}

Este capítulo presenta la metodología seguida durante el desarrollo de LIA,
la organización temporal del trabajo, la distribución de la dedicación y la
valoración económica del proyecto. La planificación se articula mediante
iteraciones que producen incrementos funcionales y permiten revisar el alcance
antes de abordar el siguiente bloque.

\section{Metodología de trabajo}

El plan de trabajo sigue Scrum, adaptado al carácter individual del TFG. El
\emph{product backlog} reúne las funcionalidades y tareas técnicas, ordenadas
según su valor y sus dependencias. Cada sprint parte de un conjunto acotado de
elementos y de un objetivo funcional. Durante la iteración se implementan,
prueban y documentan las tareas seleccionadas; al cierre se revisa el incremento
obtenido y se actualiza la prioridad del trabajo pendiente.

La adaptación mantiene los principales artefactos de Scrum: \emph{product
backlog}, \emph{sprint backlog} e incremento. El autor asumió la ejecución
técnica y el seguimiento de las iteraciones. Este enfoque facilita una
construcción incremental: primero la plataforma y la identidad; después la
configuración del dominio; y, finalmente, la gestión de oportunidades, la
cualificación y la integración de inteligencia artificial.

\subsection{Roles y responsabilidades}

La adaptación individual concentra en el autor las responsabilidades que en un
equipo Scrum se distribuyen entre varios perfiles. Como responsable del
producto, ordena el \emph{product backlog} y delimita el objetivo de cada
sprint; como facilitador del proceso, comprueba el estado de las tareas y
resuelve los bloqueos técnicos; y como equipo de desarrollo, realiza el
análisis, el diseño, la implementación y las pruebas. La tutora desempeña la
dirección académica del TFG y queda fuera de la ejecución técnica del
incremento.

Esta concentración de responsabilidades exige criterios de cierre explícitos.
Un sprint no se considera terminado únicamente porque exista código: el
incremento debe compilar, superar las comprobaciones aplicables y dejar
delimitado el trabajo pendiente antes de comenzar la siguiente iteración.

La memoria se desarrolla mediante iteraciones específicas, identificadas como
M0, M1 y sucesivas. De este modo, cada bloque documental se redacta y revisa
cuando las funcionalidades que describe han alcanzado un estado estable.

\section{Incidencias y ajustes de la planificación}

Durante el desarrollo se detectaron incidencias que obligaron a reordenar el
backlog sin alterar el objetivo general del proyecto. Los ajustes más relevantes
fueron los siguientes:

\begin{itemize}
  \item La configuración del entorno web requirió habilitar la API experimental
        de entornos de Vite para mantener estable el servidor de desarrollo con
        Nuxt en modo SPA.
  \item Las pruebas E2E de la API necesitaron una configuración específica de
        resolución de alias. La corrección se incorporó a la configuración de
        Jest antes de ampliar los escenarios automatizados.
  \item El ciclo de eventos de dominio se reforzó para publicar los eventos
        después de persistir los cambios y retirarlos del agregado mediante una
        operación explícita. Este ajuste evitó publicaciones duplicadas y mejoró
        la consistencia del workflow en ejecución.
  \item La integración de adjuntos se priorizó junto con la IA generativa, dado
        que los documentos constituyen el contexto de entrada de los análisis.
  \item Los módulos opcionales se mantuvieron fuera del núcleo para reservar la
        dedicación disponible a la cualificación de licitaciones, las pruebas y
        la memoria.
\end{itemize}

La revisión del backlog y la priorización de la ruta crítica permitieron
contener estos ajustes en una desviación total de 19 horas. Las funcionalidades
opcionales se conservaron como posibles ampliaciones y no condicionaron la
finalización del núcleo funcional.

\section{Coste de desarrollo del proyecto}
\label{sec:development-cost}

El coste de desarrollo reúne los recursos empleados una sola vez para analizar,
diseñar, implementar y validar el TFG. Incluye la dedicación del desarrollador,
la parte imputable del equipo y los consumos asociados a la campaña de pruebas.
No incluye el gasto recurrente necesario para mantener LIA disponible una vez
desplegada, que se trata por separado en la
\Cref{sec:operational-cost}.

\subsection{Coste de personal}

Para valorar el trabajo se adopta provisionalmente una tarifa de referencia de
25,67 euros por hora para el perfil de desarrollador de software. Esta cifra
procede del informe sobre perfiles profesionales informáticos de la Junta de
Andalucía \cite{juntaPerfilesInformaticos2018}; no se presenta como una tabla
salarial vigente de 2026. También se emplea, como hipótesis provisional de
cálculo, una cuota empresarial del 29,9\,\%. Ambos criterios deberán confirmarse
antes de cerrar el presupuesto definitivo.

\begin{equation}
  C_{\text{bruto}} = 320 \times 25{,}67 = 8{.}214{,}40~\text{euros}.

\section{Coste operativo de funcionamiento}
\label{sec:operational-cost}

El coste operativo es recurrente y comienza cuando la aplicación se mantiene
disponible para usuarios. No representa el esfuerzo de construir LIA. Comprende
el alojamiento de la web y la API, PostgreSQL, almacenamiento y transferencia
de PDF, correo, observabilidad, copias de seguridad y las inferencias de IA.
La topología de producción definida utiliza un servidor CX23 de Hetzner con
copias rotatorias. Su importe mensual se incorporará cuando se acrediten la
fecha de alta, el periodo y la facturación; no se asigna una cifra hipotética
para producir un presupuesto aparentemente cerrado.

Para un mes $m$, el coste se puede expresar como:

\begin{equation}
  C_{op,m} = C_{infra,m} + C_{datos,m} + C_{objetos,m} + C_{correo,m}
  + C_{obs,m} + \sum_{o \in m} C_o,
\end{equation}

donde $C_o$ es el coste de cada generación calculado con tokens de entrada,
salida y, si consta en la respuesta del proveedor, caché. La fórmula evita
extrapolar el consumo puntual del banco de pruebas como si fuera el gasto
mensual de una aplicación en servicio.

Cuando exista uso real se deberán publicar escenarios bajo, esperado y alto

documentos, tokens, reintentos y recursos de infraestructura. Hasta entonces,
la \Cref{tab:operational-cost-items} constituye un modelo de cálculo y no un
coste mensual observado.
