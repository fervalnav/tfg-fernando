\chapter{Análisis y diseño del sistema}
\label{chap:analysis}

Este capítulo transforma los requisitos del \Cref{chap:requirements} en una
propuesta funcional anterior a las decisiones de implementación. Su finalidad
es definir qué conceptos forman el sistema, cómo interactúan los usuarios con
ellos, qué secuencias deben soportarse y cómo se organiza la navegación. Las
tecnologías y los patrones empleados para materializar este diseño se abordan
en el \Cref{chap:architecture}.

Los prototipos incluidos son wireframes de baja fidelidad. Representan la
distribución y la jerarquía esperadas de cada vista, pero no fijan colores,
tipografías ni detalles visuales definitivos. Por este motivo no se utilizan
capturas de la aplicación: estas se reservan para el manual de usuario, donde
se documenta el resultado final.

\section{Modelo conceptual del dominio}

El núcleo del sistema está formado por la cuenta, las oportunidades y los
procesos configurables con los que se analizan. Una cuenta agrupa usuarios,
pipelines, workflows y catálogos reutilizables. Cada oportunidad se sitúa en un
estado de un pipeline, puede tener responsables y reúne tanto la documentación
de la licitación como los elementos que permiten cualificarla.

\begin{figure}[H]
  \centering
  \resizebox{\textwidth}{!}{
    \input{figure-sources/tikz/domain-model-overview}
  }
  \caption{Modelo conceptual general de LIA.}
  \label{fig:domain-model-overview}
\end{figure}

La \Cref{fig:domain-model-overview} distingue la definición de un proceso de su
aplicación a una oportunidad concreta. El pipeline determina el estado
comercial, mientras que el workflow establece la secuencia de análisis. Esta
separación permite que dos oportunidades recorran el mismo proceso sin
compartir respuestas, resultados ni documentos.

La cualificación requiere además diferenciar los catálogos configurables de
las instancias vinculadas a una licitación. Las plantillas expresan qué se desea
obtener; las instancias conservan el valor, el estado de generación y las
evidencias propias de una oportunidad.

\begin{figure}[H]
  \centering
  \resizebox{\textwidth}{!}{
    \input{figure-sources/tikz/qualification-domain-model}
  }
  \caption{Detalle conceptual de la cualificación y la ejecución de workflows.}
  \label{fig:qualification-domain-model}
\end{figure}

Como muestra la \Cref{fig:qualification-domain-model}, una acción de workflow
puede dirigirse a una pregunta de control, un campo personalizado, un resumen
o un documento. La acción representa el trabajo pendiente dentro del paso; el
elemento instanciado conserva el contenido que el usuario revisa. Esta
distinción evita que la modificación de una plantilla altere retroactivamente
el análisis ya realizado sobre otras oportunidades.

\section{Procesos de negocio}

\subsection{Gestión de la cartera}

El proceso comienza con la creación manual de una oportunidad. El usuario
selecciona el pipeline, el estado inicial y, cuando corresponde, los miembros
responsables. Desde la cartera puede consultar las oportunidades en formato de
tablero o lista, aplicar filtros y cambiar su estado. El descubrimiento
automático de licitaciones queda fuera de este proceso: LIA empieza a actuar
cuando el equipo decide registrar la oportunidad.

\subsection{Cualificación de una licitación}

La cualificación combina preparación documental, configuración del proceso,
ejecución de acciones y revisión humana. No se reduce a una única generación
de texto ni a una sola pantalla.

\begin{figure}[H]
  \centering
  \resizebox{\textwidth}{!}{
    \input{figure-sources/tikz/qualification-process}
  }
  \caption{Proceso funcional de cualificación de una licitación.}
  \label{fig:qualification-process}
\end{figure}

En la \Cref{fig:qualification-process}, los documentos constituyen el contexto
de las acciones posteriores. El workflow instancia únicamente los elementos
necesarios para sus pasos. El usuario puede aportar valores manuales o solicitar
asistencia de IA, pero debe conservar la capacidad de revisar y corregir el
resultado. Cuando un paso contiene una condición, el sistema evalúa la
información disponible y permite revisar la evidencia antes de continuar.

control de acceso, creación de una ejecución, almacenamiento binario y
comunicación con un proveedor externo. Los listados y operaciones de edición
convencionales siguen patrones más simples y no requieren un diagrama propio.

\section{Diseño de navegación}

La navegación parte de la cartera de oportunidades y mantiene un acceso
separado a la configuración. Dentro de una oportunidad se utiliza una
navegación contextual estable para evitar que la cualificación se fragmente en
recorridos inconexos.

\begin{figure}[H]
  \centering
  \resizebox{\textwidth}{!}{
    \input{figure-sources/tikz/navigation-map}
  }
  \caption{Mapa de navegación propuesto.}
  \label{fig:navigation-map}
\end{figure}

La \Cref{fig:navigation-map} incluye todas las áreas funcionales principales.
Las preguntas, campos y resúmenes se configuran primero como catálogos y se
consultan después como instancias dentro de una oportunidad. Esta relación se
mantiene visible en los wireframes siguientes.
